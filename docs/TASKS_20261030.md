## 3. Áp dụng vào máy Windows

Ưu tiên giải nén source mới vào **thư mục riêng**, đối chiếu rồi chuyển `.env` và dữ liệu upload của bạn sang. Dữ liệu `.env`, upload và database hiện có không nằm trong bản giao và không được xóa.

Nếu áp dụng patch vào Git checkout có cùng baseline:

```powershell
git switch -c fix/midcv-auth-runtime-20261030
git status --short
git apply --check C:\duong-dan\MIDCV_TASKS_20261030.patch
git apply C:\duong-dan\MIDCV_TASKS_20261030.patch
```

Nếu `--check` thất bại, đối chiếu file khác biệt; không dùng tùy chọn ép ghi đè thay đổi cá nhân. Patch được tạo từ đúng ZIP đính kèm, không phải từ trạng thái OneDrive hiện tại trên máy bạn.

Kiểm tra công cụ:


## 5. Nghiệm thu HTTP A01/A02/D02/D03

Dùng container kiểm thử ở bước trên:

```powershell
.\scripts\Test-MidcvTaskHttp.ps1 -ContainerName TEN_CONTAINER_VUA_TAO -Port 55439
```

Script tạo database `midcv_task_<hex>` mới và chạy `TaskHttpAcceptanceTest`. Test có chốt tên database trước khi tạo context để tránh dùng nhầm database ứng dụng.

Bộ này dùng HTTP thật, PostgreSQL thật và file thật; **mail là MOCK local, worker bị tắt**. Fixture ứng viên/HR được tạo trong database mới, không phải người dùng thật. Các kịch bản:

1. Refresh không được gọi protected API, access không được refresh.
2. Rotation; replay token cũ; session bị thu hồi cả với access còn hạn.
3. Danh sách session không lộ refresh hoặc hash; logout có hiệu lực.
4. JWT đã hết hạn bị từ chối; endpoint session ẩn danh trả 401.
5. Forgot/reset một lần; hash lưu trong DB; mật khẩu cũ bị từ chối; session cũ bị thu hồi.
6. Upload PDF: HTTP 202, file giữ đúng byte/checksum, dữ liệu document được lưu.
7. File giả PDF bị từ chối, không sinh thêm file.
8. Cố ý gây lỗi DB sau khi ghi file: không còn file/document/job/CV dang dở.
9. Cố ý làm storage không ghi được: 500 có `FILE_STORAGE_FAILED` và `X-Request-ID`, không để lại document.
10. Jobs/ranking/inspection/suspension chạy với OSIV=false và fixture có quan hệ lazy thực.

Log chỉ in method/path/status/request ID, không in token. File test mới **đã compile nhưng chưa chạy live ở môi trường tạo bản giao**. Nếu thất bại trên máy bạn, giữ log `backend/target/surefire-reports`; không đổi trạng thái task sang nghiệm thu.

## 6. SMTP và quên mật khẩu từ trình duyệt

Có thể dùng Mailpit cục bộ để kiểm tra giao thức gửi thư mà không gửi đến người khác:

```powershell
docker run -d --name midcv-task-mailpit -p 127.0.0.1:1025:1025 -p 127.0.0.1:8025:8025 axllent/mailpit
```

Nếu tên/cổng đã có dịch vụ, dùng dịch vụ đang có hoặc chọn cổng khác; không xóa container hiện hữu chỉ để chạy lệnh này. Ví dụ cấu hình `.env` cho các cổng trên:

```dotenv
EMAIL_MODE=SMTP
MAIL_FROM=noreply@midcv.local
SMTP_HOST=127.0.0.1
SMTP_PORT=1025
SMTP_AUTH=false
SMTP_STARTTLS=false
FRONTEND_PUBLIC_URL=http://localhost:3000
```

Import lại env và khởi động lại backend. Mở `http://localhost:8025`:

- Đăng ký tài khoản dùng địa chỉ kiểm thử, kiểm tra thư verify có đến Mailpit; xác minh email.
- Từ `/forgot-password`, nhập email đó; kiểm tra thư chứa `/reset-password?token=...`; mở và đặt mật khẩu mới.
- Dùng lại cùng liên kết phải thất bại; token hết 30 phút phải thất bại.
- Mật khẩu cũ không đăng nhập được; session cũ không được gọi API.
- Đăng nhập hai trình duyệt, vào Tài khoản → Bảo mật, thu hồi một session và thử API từ phiên đó.

Với SMTP thật, dùng host/port/auth/TLS do dịch vụ của bạn cung cấp. `EMAIL_MODE=MOCK` chỉ dành cho phát triển: không có thư nào được gửi ra SMTP. Địa chỉ và token từ test local không phải bằng chứng nhà cung cấp SMTP thật đã hoạt động.

## 7. A03: Google và GitHub thật

Cấu hình ở **backend**, không đưa client secret vào `NEXT_PUBLIC_*`:

```dotenv
BACKEND_PUBLIC_URL=http://localhost:8080
FRONTEND_PUBLIC_URL=http://localhost:3000
GOOGLE_OAUTH_CLIENT_ID=
GOOGLE_OAUTH_CLIENT_SECRET=
GITHUB_OAUTH_CLIENT_ID=
GITHUB_OAUTH_CLIENT_SECRET=
```

Callback đăng ký chính xác:

| Nhà cung cấp | Callback |
|---|---|
| Google | `http://localhost:8080/api/v1/auth/oauth/google/callback` |
| GitHub | `http://localhost:8080/api/v1/auth/oauth/github/callback` |

Dùng nhất quán `localhost`, không đổi qua `127.0.0.1` giữa luồng vì cookie state gắn với host. Khi deploy HTTPS, callback/public URL phải khớp cấu hình nhà cung cấp và backend phải nhận đúng scheme HTTPS qua proxy.

Chạy lần lượt cho cả hai nhà cung cấp: consent thành công; hủy consent; callback có state sai/thiếu cookie; callback cũ; redeem ticket lần hai; đăng nhập tài khoản đã liên kết; đăng nhập bằng email/mật khẩu rồi liên kết trong hồ sơ; cố liên kết cùng identity cho người dùng khác; tài khoản bị vô hiệu hóa trước redeem. Không ghi token/secret trong ảnh nghiệm thu. Chưa thực hiện các bước này thì A03 vẫn chờ nghiệm thu.

## 8. R01: SSE, reconnect, restart và lease

Đăng nhập candidate, upload CV hợp lệ trên stack có worker thật. Trong DevTools Network mở request `.../events`:

- Có `Authorization: Bearer ...`; không có token trong URL.
- Event `cv-processing-progress` có ID số từ database. Terminal snapshot có ID nội dung ổn định và không làm nhảy cursor HTTP.
- Bật Offline vài giây rồi Online: request mới gửi `Last-Event-ID`; UI không nhân đôi sự kiện đã nhận.
- Đóng modal/chuyển trang: request stream và lịch reconnect phải dừng.
- Khi xử lý xong/thất bại, stream kết thúc bình thường và không reconnect vô hạn.
- Thu hồi session khi đang stream: server đóng stream; request tiếp theo không được tiếp tục bằng access đã bị thu hồi.
- Dừng/khởi động lại backend trong lúc job RUNNING, giữ nguyên database. Sau khi lease của worker cũ hết, trạng thái được xử lý theo `JobQueue.claim`; ghi lại state/error_code và kiểm tra retry. Không đánh dấu restart/lease PASS chỉ từ test parser phía frontend.

SSE mới đọc DB mỗi giây cho các subscriber đang mở; đây là lựa chọn để tránh phát event chưa commit và hỗ trợ nhiều instance. Cần đánh giá tải nếu mở số lượng stream lớn.
